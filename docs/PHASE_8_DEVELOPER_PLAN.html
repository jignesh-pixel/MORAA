In one paragraph. Customers buy white-background e-com packs of 1, 5, 20, 50 or 100 SKUs at a flat ₹20 per SKU (GST included) through one Razorpay payment link. Paid SKUs go into a credit ledger that is separate from the rupee wallet. Each photo they then send uses one credit and makes one white-background image. Finished images go into the customer's own folder in the business Google Workspace shared drive, not into the chat. When nothing is left in progress, the customer gets one WhatsApp message with the day's folder link and the SKUs left. Everything new is switched off by default (SKU_PACKS_ENABLED=false, DRIVE_DELIVERY_ENABLED=false), so production behaves exactly as today until the owner switches it on.

1. Business rules

  • Pack sizes 1, 5, 20, 50, 100 (a setting). The 1-SKU pack works in code but is hidden from menus unless ECOM_PACK1_ENABLED=true.
  • Price ₹20 per SKU including GST, flat. It lives in the database (price_settings); python scripts/set_price.py --sku-price 25 changes it with no code change or restart. Packs already paid keep the credits they bought; new links use the new price from that moment.
  • 1 SKU = 1 white-background shot = 1 credit. Credits are valid for 90 days; buying another pack extends every unused credit to 90 days from that purchase.
  • A failed image gives its credit back (exactly once). The customer re-sends the photo for free.
  • Delivery goes to Drive. If the Drive upload still fails after 6 outbox attempts, the image is sent on WhatsApp as today. Only if that also fails is the credit given back. Nobody is left without their image or their credit.
  • Folder {phone}/ is shared with the customer's email (reader). If Google refuses (for example a non-Google address and outside sharing is blocked), the folder stays private, the customer is asked for a Google email, and an alert is raised. "Anyone with the link" is never used.
  • Email is collected at registration (Flow field, or by sending it in chat). Orders are never blocked for a missing email: the folder is created anyway and shared once the email arrives.
  • Delivered images are deleted from Drive after 90 days. Invoices stay (8-year accounting rule).
  • The wallet (rupees), the ₹50 Studio Shot and the ₹500 Catalog Pack keep working unchanged for customers who use them.

2. How it works

Buying a pack

customer taps a pack in the catalogue / list menu  (Meta "order" or "list_reply" message, retailer id pack_N)
  -> server computes the price itself (Meta cart prices are ignored)
  -> one Razorpay payment link, notes {whatsapp_id, purpose: "sku_pack", units}; recorded in razorpay_payment_links (purpose, units)
  -> Razorpay webhook / link-reconcile sweep: same once-only claim as today (audit "razorpay_payment_captured")
       purpose == sku_pack -> sku_packs.grant_pack_credits(units)   (wallet_balance untouched)
  -> receipt "20 SKUs added, valid till 6 Jan 2027" + invoice job + Usage Logs sync + folder share job

Sending photos

photo arrives -> stored (unchanged) -> customer has credits?
   yes -> consume_credit + status white_queued + credit_source "sku"  (ONE transaction, like the wallet debit today)
          -> "Photo received, 13 SKUs left" -> order run (outbox) -> process_whatsapp_white_bg (prompt unchanged)
   no  -> today's flow (buttons for wallet customers); with SKU_PACKS_ENABLED and no funds: pack menu instead of recharge

Delivering

image generated
   DRIVE_DELIVERY_ENABLED and Drive configured
      -> image kept on local disk, status "drive_pending", outbox job "drive_deliver"
      -> upload to {phone}/Images/{7 Oct 2026}/007.png (streamed, resumable upload) -> status "delivered", delivery_channel "drive"
      -> "batch_notify" job (debounced BATCH_NOTIFY_DELAY_SECONDS): when the customer has nothing in progress,
         ONE message: day-folder link + SKUs left (utility template if outside the 24-hour window)
      -> job dead after 6 attempts -> send on WhatsApp as today (delivery_channel "whatsapp"); that fails too -> credit back
   otherwise -> exactly today's WhatsApp delivery

3. Data model

Migration 0022_phase8_foundations (already on main): wider status/product/resource columns, customers.email and Drive id columns, price_settings, customer_sku_credits. 0022 is already pushed, so Phase 8 additions go into a new migration 0023_sku_packs_drive:

Table0023 changeWhy
customer_sku_creditsRebuilt (only if empty) with balance_after (CHECK >= 0) and expires_at; keeps UNIQUE(reference_id, action), CHECK quantity <> 0The database refuses a negative balance and a second grant/consume/refund for the same reference
price_settings+ effective_from, changed_byCurrent price with who/when; every change also writes an audit row (price_changed), which is the history
whatsapp_ingestions+ credit_source (wallet/sku/trial/admin), delivery_channel (whatsapp/drive), drive_file_idRefund the right thing; retention finds Drive images
razorpay_payment_links+ purpose (NULL = wallet recharge, sku_pack), unitsReconcile sweep knows what a link was for
invoice_records+ drive_file_id, drive_linkInvoice PDF in {phone}/Invoices/

Ledger rule: a customer's credits = SUM(quantity) = balance_after of the newest row. Actions: purchase (+units, reference = payment id), consume (−1, reference = ingestion id), refund (+1, reference = ingestion id), expire (−balance), clawback (−n, reference = Razorpay refund/dispute id). The Usage Logs sheet is only a view of this table and can be rebuilt at any time.

8. Outside setup

Google (business Workspace only)

  1. Create a shared drive (for example "Moraa Customers"). In the Admin console allow sharing outside the organisation for it, and with non-Google accounts if wanted.
  2. In Google Cloud under the business organisation: enable the Drive API and the Sheets API, create a service account, download its JSON key.
  3. Add the service account's email to the shared drive as Content manager.
  4. Put the key file on the server outside the code folder; set GOOGLE_SA_KEY_FILE and DRIVE_SHARED_DRIVE_ID (the id in the shared drive's URL).

Meta / WhatsApp

  1. Publish the registration Flow from docs/whatsapp_registration_flow.json (now with an email field).
  2. Create the catalogue with retailer ids pack_1, pack_5, pack_20, pack_50, pack_100; set META_CATALOG_ID; run set_price.py once to push prices.
  3. Submit a utility template for the out-of-window "images ready" notice; set BATCH_NOTIFY_TEMPLATE_NAME once approved.

Razorpay and ERPNext

  1. Test-mode keys and webhook secret; register the HTTPS webhook URL in the test dashboard.
  2. ERPNext sandbox: item code for packs (SKU_ERPNEXT_ITEM_CODE), tax templates; the accountant confirms invoice timing (at purchase) and HSN/SAC.

9. Rollout and rollback

  1. Back up the database, run scripts/release.py (migrates to 0023), start the new code. With both flags off nothing changes for customers.
  2. Turn on SKU_PACKS_ENABLED for a test number first (team phone), buy a ₹20 pack in Razorpay test mode, send one photo.
  3. Turn on DRIVE_DELIVERY_ENABLED after the Google checklist; check one folder, one share, one sheet.
  4. Rollback: switch the two flags off (immediate, no deploy). Code rollback: previous release; the 0023 downgrade refuses while credits exist, so leave the schema in place.

11. Known limits

  • Only fakes are used before the real-world session: real folder sharing, the real catalogue and real Razorpay payments are untested until then.
  • Day-folder search and file numbering are locked per process; with several server processes two uploads can rarely get the same number (Drive keeps both). A database counter can replace it if that matters.
  • Credit validity is rolling (a new pack extends unused credits). Per-pack expiry needs a decision from the owner.
  • The ₹500 Catalog Pack / Creative Studio Pack (7 styles) still delivers on WhatsApp.
  • Capacity: one shared drive holds 400,000 items, which full-speed traffic (100 images a minute) with 90-day storage would fill in about 3 days; the outbox runs one job at a time per process. See the audit report before full launch.
  • Drive image retention runs only with RETENTION_ENABLED=true.
